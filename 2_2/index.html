Ubuntu 26.04 LTS · Nginx · MySQL 8.4 · PHP 8.5 · Valkey · WordPress 7.1

WordPress Server Setup

A fast, locked-down, easy-to-grow WordPress server on one DigitalOcean droplet, built step by step from an empty Ubuntu machine.

Each step is a set of commands with the reason they matter.

Your values

Every command below updates as you type (yellow text). Values in a red dashed box are yours to type in by hand before running: passwords, admin name, email. The page never fills those in.

Step 01Create the droplet

One droplet per paid product, created in the DigitalOcean console.

  • Image: Ubuntu 26.04 (LTS) x64
  • Plan: Premium AMD, Regular CPU, 2 vCPU / 4 GB / NVMe. Check the current price in the console; the Basic 2 vCPU / 4 GB tier is $24/mo.
  • Region: FRA1 (same as your other infrastructure, close to Hungary)
  • Auth: SSH key only, never a password
  • Backups: on. Weekly costs 20% of the droplet price ($4.80 on a $24 plan), daily costs 30%.
  • Monitoring: on (free; needed for alerts in step 20)
  • Hostname and tag: something you'll recognise in the droplet list and the shell prompt

Why a dedicated droplet: problems stay contained, the OS starts clean, and you can resize, sell or retire the product without touching anything else. Resizing a single-purpose server is routine; resizing a shared one is risky.

Step 02First login, sudo user, SSH key

Stop working as root. Keep this root session open until step 04 passes.

ssh root@{{IP}}
adduser {{USER}}                 # strong password → password manager (needed for sudo)
usermod -aG sudo {{USER}}
rsync --archive --chown={{USER}}:{{USER}} /root/.ssh /home/{{USER}}
ls -la /home/{{USER}}/.ssh       # expect drwx------ and -rw------- authorized_keys

rsync --archive copies the key DigitalOcean placed for root and keeps the 700/600 permissions. SSH silently ignores keys with looser permissions.

Test from a second terminal:

ssh {{USER}}@{{IP}}
sudo whoami                      # → root

Step 03Updates, automatic security patches, swap

sudo apt update && sudo apt full-upgrade -y
sudo timedatectl set-timezone Europe/Budapest
sudo apt install unattended-upgrades -y
sudo dpkg-reconfigure -plow unattended-upgrades   # answer Yes
systemctl status unattended-upgrades

Unattended upgrades install security patches daily without you. Upgrade before editing any system config.

A friendlier text editor

sudo apt install mc -y
sudo update-alternatives --set editor /usr/bin/mcedit   # F2 save, F10 exit, F7 search

From here on, every config file is edited by hand in mcedit: open it, paste or change the lines shown, F2 to save, F10 to exit. Opening a path that doesn't exist yet creates the file on save.

Optional: nightly reboot after kernel updates

sudo mcedit /etc/apt/apt.conf.d/52unattended-reboot   # new file
Unattended-Upgrade::Automatic-Reboot "true";
Unattended-Upgrade::Automatic-Reboot-Time "04:30";

2 GB swap

sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile

Switch it on at every boot: add this line to the end of /etc/fstab. Leave the existing lines alone; a broken line in this file can stop the server from booting.

sudo mcedit /etc/fstab
/swapfile none swap sw 0 0

Use swap only when really needed:

sudo mcedit /etc/sysctl.d/99-swap.conf      # new file
vm.swappiness=10
sudo findmnt --verify                       # checks fstab: no errors = safe to reboot
sudo sysctl --system                        # applies swappiness now
free -h                                     # Swap row shows 2.0Gi

Step 04Lock down SSH

Keys only, no root login. The riskiest step: keep both terminals open.

1. Check the override folder first

ls /etc/ssh/sshd_config.d/
sudo grep -H . /etc/ssh/sshd_config.d/*.conf   # usually 50-cloud-init.conf

If any file there says PasswordAuthentication yes (or sets one of the four settings below differently), change it:

sudo mcedit /etc/ssh/sshd_config.d/50-cloud-init.conf   # → PasswordAuthentication no

Why this comes first: the Include /etc/ssh/sshd_config.d/*.conf line sits at the top of sshd_config, and sshd keeps the first value it reads. Anything in that folder beats what you write in the main file. This is the classic "I set it to no, but passwords still work" trap on Ubuntu.

2. Edit the main config

sudo mcedit /etc/ssh/sshd_config                # F7 to search each setting

Make these four lines read exactly like this. If a line starts with #, remove the #; if it's missing, add it:

PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
  • PermitRootLogin no: nobody logs in as root, not even with a key.
  • PasswordAuthentication no: bots guessing passwords get nowhere.
  • KbdInteractiveAuthentication no: closes the second, lesser-known password route.
  • PubkeyAuthentication yes: SSH keys are the only way in.

3. Validate, reload, verify

sudo sshd -t && sudo systemctl reload ssh
sudo sshd -T | grep -Ei '^(permitrootlogin|passwordauthentication|kbdinteractiveauthentication|pubkeyauthentication) '
  • sshd -t checks syntax before the reload. A typo here is how people lock themselves out.
  • sshd -T prints the effective settings after every file is merged. Expect no no no yes.
  • reload keeps open sessions alive; only new logins use the new rules.

From a third terminal: ssh {{USER}}@{{IP}} works, ssh root@{{IP}} gets Permission denied. Then close the root session.

Alternative: put the same four lines in a new file, /etc/ssh/sshd_config.d/00-hardening.conf. It's read before everything else, so it wins over both files, and OpenSSH updates never ask about it.

Step 05Firewall

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH           # before enable, or you cut your own session
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose

Only three ports face the internet. MySQL and Valkey listen on localhost and stay unreachable from outside.

Step 06fail2ban for SSH

sudo apt install fail2ban -y
sudo mcedit /etc/fail2ban/jail.local            # new, empty file

Type or paste this, then save (F2) and exit (F10):

[sshd]
enabled  = true
maxretry = 5
findtime = 10m
bantime  = 1h
  • [sshd]: the jail that watches SSH logins. Everything below it applies to this jail only.
  • maxretry + findtime: 5 failed logins within 10 minutes…
  • bantime: …bans that IP for an hour.
sudo systemctl enable --now fail2ban
sudo systemctl restart fail2ban                 # picks up jail.local if fail2ban was already running
sleep 3; sudo fail2ban-client status sshd

If the status call says Failed to access socket path, the server was still starting; run it again. To change a value later: edit jail.local, then sudo fail2ban-client reload.

Step 07Nginx

sudo apt install nginx -y
sudo systemctl enable --now nginx
curl -I http://{{IP}}                                   # 200, Nginx welcome page

Hide the Nginx version number. Search (F7) for server_tokens inside the http { block and remove the # in front of it:

sudo mcedit /etc/nginx/nginx.conf
server_tokens off;
sudo nginx -t && sudo systemctl reload nginx
curl -sI http://{{IP}} | grep -i '^server'             # Server: nginx (no version)

Why Nginx over Apache: one event-driven process handles thousands of connections, which leaves more of 4 GB for PHP and MySQL. It has no .htaccess, so any rule a plugin writes there does nothing here.

Step 08MySQL 8.4

sudo apt install mysql-server -y
sudo mysql_secure_installation
  • VALIDATE PASSWORD component: N (adds friction, no real gain on a single-user server)
  • Remove anonymous users: Y · Disallow root login remotely: Y · Remove test database: Y · Reload privileges: Y

No MySQL root password is set, and none is needed: on Ubuntu, MySQL trusts your Linux login. sudo mysql gets you in as the MySQL root user.

Give InnoDB real memory

sudo mcedit /etc/mysql/mysql.conf.d/99-wordpress.cnf   # new file
[mysqld]
innodb_buffer_pool_size = 1G
sudo systemctl restart mysql
sudo mysql -e "SELECT @@innodb_buffer_pool_size/1024/1024 AS buffer_pool_mb;"

Rough memory budget on 4 GB:

MySQL ~1.2 GB
Valkey
PHP-FPM ≤ ~1.6 GB
OS + Nginx

Step 09PHP 8.5 FPM

sudo apt install php-fpm php-mysql php-curl php-gd php-mbstring php-xml php-zip \
  php-intl php-bcmath php-imagick php-soap php-redis -y
php -v
systemctl status php8.5-fpm

PHP 8.5 is Ubuntu 26.04's default. Before building, check that your paid plugins list PHP 8.5 support.

Settings as one drop-in file

sudo mcedit /etc/php/8.5/fpm/conf.d/99-wordpress.ini   # new file
memory_limit = 512M
upload_max_filesize = 128M
post_max_size = 128M
max_execution_time = 300
max_input_vars = 5000
expose_php = Off
opcache.memory_consumption = 256
opcache.interned_strings_buffer = 16
opcache.max_accelerated_files = 20000
opcache.revalidate_freq = 2

Your own file next to php.ini: every WordPress-specific value in one place, easy to reread later, and never overwritten by PHP updates. It takes effect with the FPM restart below.

SettingWhy
memory_limit 512MA per-request ceiling, not a reservation. Typical requests use 60–150 MB; Elementor saves and big WooCommerce reports can spike past the 128M default.
upload / post 128MVideos, PDFs and slide decks through the media library. post_max_size must be ≥ upload_max_filesize.
max_execution_time 300Imports, exports and migrations. Only works if Nginx waits too (fastcgi_read_timeout 300 in step 11).
max_input_vars 5000Elementor saves are large forms. At the default 1000, saves are cut short with no error.
expose_php OffRemoves the X-Powered-By: PHP header.
opcache.*Compiled PHP stays in RAM. WordPress + WooCommerce + Elementor Pro + other plugins can exceed 10,000 files, hence 20,000.

Worker pool

sudo sed -i \
  -e 's/^pm = .*/pm = dynamic/' \
  -e 's/^pm.max_children = .*/pm.max_children = 15/' \
  -e 's/^pm.start_servers = .*/pm.start_servers = 4/' \
  -e 's/^pm.min_spare_servers = .*/pm.min_spare_servers = 2/' \
  -e 's/^pm.max_spare_servers = .*/pm.max_spare_servers = 6/' \
  -e 's/^;*pm.max_requests = .*/pm.max_requests = 500/' \
  /etc/php/8.5/fpm/pool.d/www.conf
grep -E '^pm' /etc/php/8.5/fpm/pool.d/www.conf
sudo php-fpm8.5 -t && sudo systemctl restart php8.5-fpm
php-fpm8.5 -i | grep -E '^(memory_limit|max_input_vars|opcache.memory_consumption) '

max_children ≈ RAM you can give PHP ÷ average worker size (~100 MB) → 15 on 4 GB. Once real traffic arrives, check the actual size with ps -ylC php-fpm8.5 --sort:rss and adjust. max_requests 500 recycles workers so slow memory leaks in plugins never pile up.

Step 10Object cache (Valkey)

Valkey is the open-source continuation of Redis: same protocol, so the WordPress plugin called "Redis Object Cache" works with it unchanged.

sudo apt install valkey-server valkey-tools -y
dpkg -L valkey-server | grep '\.conf$'          # expect /etc/valkey/valkey.conf
sudo mcedit /etc/valkey/valkey.conf

The file is long and mostly comments. Search (F7) for each setting, remove the # and set the value:

maxmemory 256mb
maxmemory-policy allkeys-lru
sudo systemctl enable valkey-server && sudo systemctl restart valkey-server
valkey-cli ping                                   # PONG
valkey-cli config get maxmemory
valkey-cli config get maxmemory-policy
  • maxmemory 256mb caps the cache so it can't eat PHP's memory.
  • allkeys-lru drops the least recently used entries when full, so hot data stays cached.
  • Search for # maxmemory <bytes> and # maxmemory-policy: similar-looking lines such as maxmemory-samples or maxmemory-clients are different settings. Leave them.
  • config get checks the running value, which is more reliable than reading the file.

Step 11Site folder and Nginx server block

sudo mkdir -p /var/www/{{SITE}}/{public_html,backups}
sudo chown -R www-data:www-data /var/www/{{SITE}}
sudo usermod -aG www-data {{USER}}     # log out and back in to apply
sudo mcedit /etc/nginx/sites-available/{{SITE}}
server {
    listen 80;
    listen [::]:80;
    server_name {{DOMAIN}} www.{{DOMAIN}};

    root /var/www/{{SITE}}/public_html;
    index index.php;
    autoindex off;
    client_max_body_size 128M;          # = PHP upload limit

    access_log /var/log/nginx/{{SITE}}.access.log;
    error_log  /var/log/nginx/{{SITE}}.error.log;

    gzip on;
    gzip_vary on;
    gzip_comp_level 5;
    gzip_min_length 1000;
    gzip_types text/plain text/css text/xml application/json application/javascript application/xml image/svg+xml;

    # 1. Exact matches are checked before any regex
    location = /wp-config.php { deny all; }
    location = /xmlrpc.php    { deny all; }

    # 2. Regex denies must come BEFORE the PHP block: first regex match wins
    location ~ /\.(?!well-known/) { deny all; }             # .git, .env, .ht*
    location ~* ^/wp-content/uploads/.*\.php$ { deny all; } # no PHP in uploads

    # 3. WordPress permalinks
    location / {
        try_files $uri $uri/ /index.php$is_args$args;
    }

    # 4. PHP
    location ~ \.php$ {
        include snippets/fastcgi-php.conf;
        fastcgi_pass unix:/run/php/php8.5-fpm.sock;
        fastcgi_read_timeout 300;         # = max_execution_time
    }

    # 5. Static files: 30-day browser cache
    location ~* \.(?:css|js|mjs|jpe?g|png|gif|webp|avif|svg|ico|woff2?)$ {
        expires 30d;
        access_log off;
    }
}
sudo ln -s /etc/nginx/sites-available/{{SITE}} /etc/nginx/sites-enabled/
sudo rm /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx

Step 12DNS

At your DNS host (e.g. DigitalOcean → Networking → Domains): an A record for @ → {{IP}}, plus www or a wildcard * → {{IP}}.

dig +short {{DOMAIN}}
dig +short www.{{DOMAIN}}          # both must print {{IP}} before step 13

If you later turn on Cloudflare's proxy, Nginx and fail2ban will see Cloudflare's IPs instead of visitors' until you configure set_real_ip_from. We didn't proxy.

Step 13TLS, HTTP/2, security headers

sudo apt install certbot python3-certbot-nginx -y
sudo certbot --nginx -d {{DOMAIN}} -d www.{{DOMAIN}} --redirect
sudo certbot renew --dry-run         # proves auto-renewal works, not just that the timer exists

Certbot also added its own TLS settings (options-ssl-nginx.conf). Don't add your own ssl_protocols or ssl_ciphers lines: a duplicate makes nginx -t fail.

Add HTTP/2 and security headers

Certbot rewrote the site file from step 11. Open it again:

sudo mcedit /etc/nginx/sites-available/{{SITE}}

Below is the whole file as Certbot leaves it. Everything is already there except the five green lines: type those in, in exactly that spot, and change nothing else.

server {
    server_name {{DOMAIN}} www.{{DOMAIN}};

+     http2 on;
+     add_header Strict-Transport-Security "max-age=31536000" always;
+     add_header X-Frame-Options "SAMEORIGIN" always;
+     add_header X-Content-Type-Options "nosniff" always;
+     add_header Referrer-Policy "strict-origin-when-cross-origin" always;

    root /var/www/{{SITE}}/public_html;
    index index.php;
    autoindex off;
    client_max_body_size 128M;          # = PHP upload limit

    access_log /var/log/nginx/{{SITE}}.access.log;
    error_log  /var/log/nginx/{{SITE}}.error.log;

    gzip on;
    gzip_vary on;
    gzip_comp_level 5;
    gzip_min_length 1000;
    gzip_types text/plain text/css text/xml application/json application/javascript application/xml image/svg+xml;

    # 1. Exact matches are checked before any regex
    location = /wp-config.php { deny all; }
    location = /xmlrpc.php    { deny all; }

    # 2. Regex denies must come BEFORE the PHP block: first regex match wins
    location ~ /\.(?!well-known/) { deny all; }             # .git, .env, .ht*
    location ~* ^/wp-content/uploads/.*\.php$ { deny all; } # no PHP in uploads

    # 3. WordPress permalinks
    location / {
        try_files $uri $uri/ /index.php$is_args$args;
    }

    # 4. PHP
    location ~ \.php$ {
        include snippets/fastcgi-php.conf;
        fastcgi_pass unix:/run/php/php8.5-fpm.sock;
        fastcgi_read_timeout 300;         # = max_execution_time
    }

    # 5. Static files: 30-day browser cache
    location ~* \.(?:css|js|mjs|jpe?g|png|gif|webp|avif|svg|ico|woff2?)$ {
        expires 30d;
        access_log off;
    }

    listen [::]:443 ssl ipv6only=on; # managed by Certbot
    listen 443 ssl; # managed by Certbot
    ssl_certificate /etc/letsencrypt/live/{{DOMAIN}}/fullchain.pem; # managed by Certbot
    ssl_certificate_key /etc/letsencrypt/live/{{DOMAIN}}/privkey.pem; # managed by Certbot
    include /etc/letsencrypt/options-ssl-nginx.conf; # managed by Certbot
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem; # managed by Certbot
}

server {
    if ($host = www.{{DOMAIN}}) {
        return 301 https://$host$request_uri;
    } # managed by Certbot

    if ($host = {{DOMAIN}}) {
        return 301 https://$host$request_uri;
    } # managed by Certbot

    listen 80;
    listen [::]:80;
    server_name {{DOMAIN}} www.{{DOMAIN}};
    return 404; # managed by Certbot
}

How to read the file:

  • First server { } block = HTTPS. It's your step 11 config. Certbot removed your two listen 80 lines from it and appended the six # managed by Certbot lines at the bottom (port 443 + certificate paths). The new lines go here, because this is the block that serves the site.
  • Second server { } block = redirect. Certbot wrote it. Anyone arriving on plain http:// gets sent to https://. Don't add anything here: it never serves a page, so headers here would do nothing.
  • Never edit or move a line marked # managed by Certbot. Certbot relies on them when you later add a domain or reinstall the certificate.
  • The copy button on this block copies only the five new lines.
New lineWhat it does
http2 onLoads all CSS, JS and images over one connection instead of many.
Strict-Transport-SecurityHSTS: for a year, browsers go straight to HTTPS and refuse plain HTTP for this domain.
X-Frame-OptionsOther sites can't embed your pages in an iframe (stops click-jacking tricks).
X-Content-Type-OptionsBrowsers trust the declared file type instead of guessing, so an uploaded "image" can't run as a script.
Referrer-PolicyOther sites see only your domain when a visitor clicks away, not the full URL they were on.

always means the header is sent on error pages (403, 404) too, not only on successful ones.

sudo nginx -t && sudo systemctl reload nginx
curl -sI https://{{DOMAIN}} | grep -iE '^(HTTP|strict|x-frame|x-content|referrer)'
# HTTP/2 403 is expected until WordPress is installed (empty webroot)

Step 14Database and a single-purpose user

openssl rand -base64 24          # generate the DB password → password manager
sudo mysql
CREATE DATABASE {{SITE}}_wp CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

Edit before runningDon't paste the next line as it is. Replace [[PASTE_GENERATED_PASSWORD]] with the password openssl just printed. Keep the single quotes around it: 'Xk3v…'. This is the password WordPress will use in step 15, so save it in your password manager first.

CREATE USER '{{SITE}}_user'@'localhost' IDENTIFIED BY '[[PASTE_GENERATED_PASSWORD]]';
GRANT ALL PRIVILEGES ON {{SITE}}_wp.* TO '{{SITE}}_user'@'localhost';
EXIT;

The user can reach one database, only from localhost. utf8mb4 stores every character, emoji included. FLUSH PRIVILEGES isn't needed after CREATE USER and GRANT.

Step 15Install WordPress

Download and configure from the terminal, then finish in the browser. Do parts 2 and 3 back to back.

1. Install WP-CLI (WordPress's command-line tool)

curl -O https://raw.githubusercontent.com/wp-cli/builds/gh-pages/phar/wp-cli.phar
php wp-cli.phar --info
chmod +x wp-cli.phar && sudo mv wp-cli.phar /usr/local/bin/wp
sudo install -d -o www-data -g www-data /var/www/.wp-cli   # WP-CLI cache for www-data

2. Download WordPress and write wp-config.php

cd /var/www/{{SITE}}/public_html
sudo -u www-data wp core download
sudo -u www-data wp config create --dbname={{SITE}}_wp --dbuser={{SITE}}_user --prompt=dbpass
# ↑ asks for the DB password: paste the one from step 14
sudo -u www-data wp config set DISALLOW_FILE_EDIT true --raw   # no code editor in wp-admin
sudo -u www-data wp config set FS_METHOD direct                # updates without FTP prompts
sudo -u www-data wp config set WP_REDIS_HOST 127.0.0.1
sudo -u www-data wp config set WP_REDIS_PORT 6379 --raw
sudo -u www-data wp config set DISABLE_WP_CRON true --raw      # real cron in step 16
sudo -u www-data wp config set WP_POST_REVISIONS 10 --raw      # keeps wp_posts lean
  • config create generates fresh salts and tests the database connection before writing the file.
  • --prompt=dbpass asks for the password interactively, so it never lands in shell history.
  • Everything runs as www-data, so file ownership is right from the start.

3. Finish in the browser, straight away

Do this now, not laterFrom the moment WordPress is downloaded until you finish this screen, anyone who opens your domain sees the same install form and could complete it first, becoming the admin of your site. Open the domain right after part 2 and finish within a few minutes.

Open https://{{DOMAIN}}. Because wp-config.php already exists, WordPress skips the database questions and shows the "Welcome" screen:

FieldWhat to enter
Site TitleAnything; you can change it later in Settings → General.
UsernameNot admin and not your name. It can't be changed later without a plugin or SQL.
PasswordKeep the strong suggested one. Save it in your password manager before clicking Install.
Your EmailA real address: password resets and security alerts go here.
Search engine visibilityTick "Discourage search engines". You untick it at launch (step 22).

Click Install WordPress, log in, then check from the terminal that the only administrator is you, and lock the config file:

sudo -u www-data wp user list --fields=user_login,user_email,roles   # exactly one line: you
sudo chmod 600 wp-config.php

If the domain shows a login page instead of the Welcome screen and you didn't install it, someone beat you to it. Don't use that site: drop the database and repeat steps 14–15.

Alternative: install from the terminal

Same result without the browser, and without the open window, because WordPress is installed the moment the command finishes.

Edit before runningReplace the three values in red dashed boxes: the site title, an admin username that isn't admin or your name, and your real email. The admin password is asked for interactively.

sudo -u www-data wp core install --url=https://{{DOMAIN}} --title="[[SITE TITLE]]" \
  --admin_user=[[PICK_A_NON_OBVIOUS_NAME]] --admin_email=[[YOUR_EMAIL]] \
  --prompt=admin_password --skip-email
sudo -u www-data wp option update blog_public 0     # = the "discourage search engines" checkbox
sudo chmod 600 wp-config.php

Minor WordPress updates (security fixes) install automatically by default; nothing to set for that.

Step 16Real cron and nightly database dumps

Test both commands by hand first:

sudo -u www-data wp cron event run --due-now --path=/var/www/{{SITE}}/public_html
sudo -u www-data wp db export - --path=/var/www/{{SITE}}/public_html | head -c 300
sudo crontab -u www-data -e
*/5 * * * * /usr/local/bin/wp cron event run --due-now --path=/var/www/{{SITE}}/public_html --quiet
15 3 * * * /usr/local/bin/wp db export - --path=/var/www/{{SITE}}/public_html --quiet | gzip > /var/www/{{SITE}}/backups/db-$(date +\%F).sql.gz && find /var/www/{{SITE}}/backups -name 'db-*.sql.gz' -mtime +14 -delete
  • WP-CLI runs cron inside PHP directly, so it doesn't depend on Nginx, TLS or DNS, can't be served from cache, and can't be banned by fail2ban.
  • In crontab, % means newline, so it's escaped as \%.
  • If the export complains about the PROCESS privilege and tablespaces, add --no-tablespaces=true after export -.

Step 17File permissions

sudo chown -R www-data:www-data /var/www/{{SITE}}/public_html
sudo find /var/www/{{SITE}}/public_html -type d -exec chmod 755 {} +
sudo find /var/www/{{SITE}}/public_html -type f -exec chmod 644 {} +
sudo chmod 600 /var/www/{{SITE}}/public_html/wp-config.php

A conscious trade-off: www-data owns the code, so dashboard updates work (FS_METHOD direct), but a compromised plugin could also rewrite code. The stricter setup (you own the code, www-data owns only uploads/) means every update goes through WP-CLI. We chose convenience. Being in the www-data group only gives you read access at 644; edit with sudo -u www-data.

Step 18fail2ban for WordPress logins

1. The filter: what a failed login looks like

sudo mcedit /etc/fail2ban/filter.d/wordpress-login.conf   # new file
[Definition]
failregex = ^<HOST> -[^"]*"POST /wp-login\.php[^"]*" 200
ignoreregex =

The pattern reads: a line in the access log where the visitor's IP (<HOST>) sent a POST to wp-login.php and got status 200 back.

2. The jail: what to do about it

sudo mcedit /etc/fail2ban/jail.d/wordpress.conf           # new file
[wordpress-login]
enabled  = true
filter   = wordpress-login
logpath  = /var/log/nginx/{{SITE}}.access.log
port     = http,https
maxretry = 10
findtime = 10m
bantime  = 4h

filter points to the file from part 1 (without .conf), logpath is the log to watch, port is what gets blocked for a banned IP.

3. Test, load, check

sudo fail2ban-regex /var/log/nginx/{{SITE}}.access.log /etc/fail2ban/filter.d/wordpress-login.conf
sudo fail2ban-client reload
sudo fail2ban-client status wordpress-login

Step 22Before launch

  1. SSL Labs at ssllabs.com/ssltest: aim for A. If it says it's at capacity, try again later.
  2. Mozilla Observatory: B is the realistic target (step 13).
  3. Stripe: test mode until a full test purchase, renewal and refund go through.
  4. Test one restore: a DigitalOcean backup onto a throwaway droplet, or last night's dump into a scratch database. An untested backup doesn't count.
  5. Manual All-in-One export before heavy building starts.
  6. Launch-day resize: resize up (e.g. to 8 GB) the day before a big email blast and back down after. Choose "CPU and RAM only" so you can shrink again; a disk resize can't be undone. Raise pm.max_children while you're larger.
  7. Open to search engines:
